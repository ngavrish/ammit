# ammit on Postgres

ammit kept its whole record in one SQLite file, `/data/ammit.db` on the
`agentic-v-model_ammit-data` volume. The file reached about 14 GB, most of it
the search index, and SQLite has one writer: an archive pass, a long chart
query or a backfill held the lock while every event the pipeline sent waited
behind it. This change moves the record to Postgres and keeps every answer the
service gives the same.

This page is the plan and the procedure: the schema, what was rewritten and
why, how the live SQLite file gets copied in without stopping the watchdog for
more than a few minutes, and how to go back.

## What changes, in one table

| | SQLite | Postgres |
|---|---|---|
| driver | `modernc.org/sqlite` | `github.com/jackc/pgx/v5` (`stdlib`) |
| where | `AMMIT_DB=/data/ammit.db` | `AMMIT_DSN` (no password) + Vault |
| writer / readers | one file, WAL, a read-only second handle | one pool for writes, one pool whose every transaction is read-only |
| events | one table | partitioned by UTC month (`events_y2026m11`, ...) |
| payload | `TEXT` | `jsonb` |
| ids | `INTEGER PRIMARY KEY AUTOINCREMENT` | `bigint GENERATED BY DEFAULT AS IDENTITY` |
| search | FTS5 external-content tables (`search_fts`, `kb_fts`) | a generated `tsvector` column (`words`) + GIN index |
| archive | `archive/ammit-YYYY-MM.db`, `ATTACH`ed | the `archive` schema in the same database |
| schema | `CREATE ... IF NOT EXISTS` on every start | the same, under an advisory lock, recorded in `ammit_schema` |

The data directory stays: documents, `progress.log` and the configuration
store (`/data/config`) are files as they were. `AMMIT_DATA` (default `/data`)
replaces `AMMIT_DB` for finding them.

## Configuration

```
AMMIT_DSN            postgres://ammit@ammit-postgres:5432/ammit?sslmode=disable
AMMIT_PG_VAULT       ammit/postgres.env        the sut/ secret holding the password
AMMIT_PG_VAULT_KEY   POSTGRES_PASSWORD         the KEY=value line in it (default)
VAULT_ADDR           http://vault:8200
SUT_VAULT_TOKEN      the stack's read token
```

The password is never in the environment and never in a file. ammit reads
`$VAULT_ADDR/v1/sut/data/ammit/postgres.env`, takes the `POSTGRES_PASSWORD=`
line of its `content` - the same store, token and shape every other service
reads through `deploy/vault/vault-env.sh` - and hands it to pgx in memory. A
DSN that carries a password is refused at start. Nothing logs the DSN: `/health`
and the start line say `postgres://host:port/database`.

ammit waits up to a minute for Vault and thirty seconds for Postgres at start,
then exits; `restart: always` brings it back. The database itself needs Vault
only once, when it makes its data directory (see the compose change below), so
a Vault outage does not stop a running record or a restart of Postgres.

## Schema

Every table keeps its name, its columns and its indexes. The types are the
Postgres spellings of what SQLite stored: `REAL` is `double precision`,
`INTEGER` is `bigint`, `BLOB` (`kb_chunks.vec`) is `bytea`, `TEXT` is `text`.

### events, by month

```sql
CREATE TABLE events (
    id bigint GENERATED BY DEFAULT AS IDENTITY,
    at double precision NOT NULL,
    kind text NOT NULL, run text, phase text, session text, agent text, branch text,
    payload jsonb NOT NULL,
    PRIMARY KEY (id, at)
) PARTITION BY RANGE (at);
CREATE TABLE events_default PARTITION OF events DEFAULT;
```

- One partition per UTC month, named `events_yYYYYmMM`, bounded by the epoch
  seconds of the month's first instant and the next month's.
- `ensurePartitions` makes this month's and next month's table on start and on
  every tick (one catalog question a month after the first), so an event never
  waits on DDL. A partition is made beside `events` and attached, after moving
  in anything `events_default` caught for that month - `CREATE ... PARTITION OF`
  would refuse while such a row exists, and a client may send an `at` a month
  ahead.
- The partition key has to be in the primary key; `id` alone stays unique
  because one sequence hands it out. Lookups by `id` probe each month's index.
- The indexes (`events_run`, `events_kind`, `events_span`, `events_phase`) are
  declared on `events` and exist on every partition.
- Old months can later be detached or dropped whole. Nothing does that today:
  `archive` still moves finished runs by `retention.days`, as before.

### payload as jsonb

`payload` is the event as Go marshalled it, stored as `jsonb`. Two things
jsonb refuses that SQLite kept: `\u0000` inside a string and a NUL byte in any
text column. `store` replaces both with U+FFFD before writing (`noNUL`,
`clean`); every other text argument goes through `clean` too.

jsonb keeps keys in its own order and prints with spaces. What a caller reads
is not changed by that - see "What a caller reads" below.

### search

`search_text` gains a generated column and an index:

```sql
words tsvector GENERATED ALWAYS AS
      (to_tsvector('simple', regexp_replace(body, '[^[:alnum:]]+', ' ', 'g'))) STORED
CREATE INDEX search_text_words ON search_text USING gin (words);
```

The expression is FTS5's `unicode61` tokenizer in SQL: every run of letters
and digits is a word, everything else separates them, case is folded and
nothing is stemmed - so `server/main.go` is the words server, main and go, as
it was (Postgres's own parser would keep it as one file-path token that
`main.go` does not match). `/search` builds a `websearch_to_tsquery` of quoted
phrases from the same runs, which never fails to parse, and orders by
`ts_rank(words, q, 1)` where FTS5 ordered by `bm25`.

There is no second index to rebuild: a row is its own index entry. `ftsLost`
and the FTS5 rebuild are gone; `rebuildFTS` now only writes the
`search_meta.fts_generation` marker, which still decides whether a start
re-reads every event. `kb_chunks` gets the same `words` column in place of the
`kb_fts` table.

PR #158 (documents leave the index) touches the same code. Whichever lands
second rebases: with #158, `indexDocument`/`backfillDocuments` go and
`dropDocuments` is a `DELETE ... WHERE source='document'`; nothing here
conflicts with it beyond the lines both edit.

### functions the queries lean on

Three, made by `migrate` (`server/schema.go`), so the hundred queries do not
each spell out the difference:

- `jnum(jsonb)` - json_extract's number: a JSON number is itself, `true` and
  `false` are 1 and 0, a numeric string is its number, anything else NULL.
- `round(double precision, integer)` - Postgres rounds floats only to whole
  numbers, half to even. This one rounds the double's exact decimal value half
  away from zero, as SQLite does: `round(114.55, 1)` is 114.5, because 114.55
  is 114.5499999999999972. `round(x, 0)` is SQLite's `round(x)`.
- `lead_int(text)` - SQLite's `CAST(text AS INTEGER)`: the leading digits, 0
  when there are none, NULL for NULL.

### the rest

- `ammit_schema (version, at)`: which schema the database was brought to.
  `schemaSteps` holds any future change that is not idempotent DDL.
- `archive` schema: `archive.runs`, `archive.events`, `archive.judgements`,
  `archive.limits`, made by the first archive pass (`LIKE public.<table>`).
- The columns added to `calls` over time (`why`, `request`, `adhoc`) are
  `ADD COLUMN IF NOT EXISTS` in `migrate`, so a fresh database and an old one
  end the same.

## Rewrites

Every query string in `server/` was ported by hand; the rules, so a reviewer
can check any of them:

| SQLite | Postgres | where |
|---|---|---|
| `?`, `?1` | `$1` - translated at run time by `rebind` (DB and Tx in `db.go`), outside quotes and comments | everywhere |
| `json_extract(p,'$.a.b')` as text | `p->'a'->>'b'` | filters, `coalesce(..., '')`, joins |
| `json_extract(p,'$.a')` as a number | `jnum(p->'a')` | sums, comparisons with numbers, `coalesce(..., 0)` |
| `json_extract(p,'$.a')` handed to a caller | `p->'a'` (jsonb, rendered as SQLite would) | `/requests`, `/logs` |
| `json_extract(p,'$.ok') IN (0,'false')` | `p->'ok' IN ('0','false','"false"')` | `progress.go` |
| text column `payload LIKE ?` | `payload::text ILIKE ?` | `networkRefused` |
| `INSERT OR IGNORE` | `ON CONFLICT DO NOTHING` | lifts, runs, watchdog |
| `INSERT OR REPLACE` | `ON CONFLICT (key) DO UPDATE SET ...` | flows, model_streams, phase_model_times |
| `LastInsertId()` | `INSERT ... RETURNING id` | events, documents, search_text, queue, cycles, kb |
| `IS NOT ?` | `IS DISTINCT FROM ?` | answers, kb |
| scalar `max(a,b)` / `min(a,b)` | `greatest` / `least` | prices, compare, charts |
| `sum(a > b)` | `sum((a > b)::int)` | answers, charts |
| `CAST(x AS INTEGER)` (truncates) | `trunc(x)::bigint`, `lead_int(text)` | charts, liftHistory |
| `ifnull` | `coalesce` | everywhere |
| `instr(a,b)` | `strpos(a,b)` | liftHistory, answers |
| `group_concat(DISTINCT k)` | `string_agg(DISTINCT k, ',')` | `/calls/targets`, charts |
| `GLOB '[A-Z]*-[0-9]*'` | `~ '^[A-Z].*-[0-9]'` | keeper |
| `LIKE` (case-insensitive in SQLite) | `ILIKE` | everywhere |
| `strftime('%s','now')` | `floor(extract(epoch from now()))::float8` | charts |
| `date(x,'unixepoch')` | `to_char(to_timestamp(x) AT TIME ZONE 'UTC', 'YYYY-MM-DD')` | `/stats/model-turns?by=day` |
| `HAVING alias > 1` | `HAVING count(*) > 1` | `/calls/*`, charts |
| a bare column beside an aggregate | `max(column)`, or the column in `GROUP BY` | `/calls/repeated`, `spinningSessions`, charts |
| `FROM (SELECT ...)` with no alias | `... ) AS s` (Postgres before 16 asks) | compare, charts |
| `ORDER BY x DESC` (NULLs last in SQLite) | `ORDER BY x DESC NULLS LAST` | `/runs`, `/requests?slow`, charts |
| `pragma_table_info`, `sqlite_master` | `information_schema.columns`, `pg_inherits` | prices, schema |
| `main.<table>` in a run-scoped chart | `public.<table>` | `scope()` |
| `ATTACH` / `VACUUM` / FTS `rebuild` | the archive schema, autovacuum, nothing | `archive` |

The charts' own SQL (`panels.json`, `lifetime.json`, `heal.json`,
`model.json`) is ported under the same rules.

### What a caller reads

`/query`, the charts and every listing scan cells of any type, and SQLite
handed them over in its own shapes. `sqlCell` (`db.go`) gives back the same:

- `numeric` (a sum or average of integers) is a JSON number, not the string
  the driver carries it in;
- a boolean (a comparison in a select list) is 1 or 0;
- `jsonb` is what `json_extract` returned: a scalar is itself (`true` is 1),
  an object or array is its text, compact and with Go's key order - so
  `SELECT payload FROM events` answers byte for byte what it did.

Column names of expressions are Postgres's (`?column?`, `float8`) where SQLite
used the expression's text; clients read rows by position.

### /query and the charts are Postgres SQL now

SQL a caller writes is run as written, so the callers had to change. Every
caller in agentic-v-model is ported in its own PR (see below), into the
dialect SQLite 3.38+ and Postgres share (`->>`, `CAST(... AS DOUBLE
PRECISION)`, `CASE`) - so it works against the SQLite ammit today and the
Postgres one after, and can be merged first.

The panels people saved on the page live in ammit's configuration store
(`/data/config/charts-local.json`), not in a repository. The eleven there on
2026-11-06 are ported in `docs/charts-local.postgres.json`; any saved after
that are ported by hand at the cut-over.

The read-only pool is `default_transaction_read_only=on`, and every caller
query runs in a `BEGIN READ ONLY` transaction of its own, so a `set_config`
inside one cannot outlive it. pgx's extended protocol refuses a second
statement (`SELECT 1; DROP TABLE runs`). For a further line, give ammit's
readers a role with SELECT only.

## What is not identical, and why it is acceptable

- **Search order.** The same words match; among matches the order is
  `ts_rank` (with length normalisation) rather than bm25, ties by id. The
  reply says `"engine":"fts"` where it said `"fts5"`; `/kb/ask` says `"fts"` /
  `"vector+fts"`, and a word-ranked score is the rank (about 0.06) where it was
  -bm25 (about 1e-6). Nothing in either repository reads those labels.
- **Diacritics.** unicode61 folded é to e; the `simple` configuration does not.
- **Float sums.** Postgres adds a group's floats in its own order; a sum can
  differ in the 15th digit, and a value on a rounding boundary can then round
  the other way (`17.55` vs `17.54999`). Seen once in 170 compared answers.
- **Very long bodies.** A tsvector is at most 1 MB; a document body that big
  makes its `search_text` insert fail (logged), where FTS5 indexed it. With
  #158 documents leave the index and event prose is far below this.
- **Typing.** SQLite kept whatever it was given in any column; Postgres keeps
  the column's type. A payload number that is a string ("12") is read by
  `jnum` as 12, as SQLite's arithmetic read it; a comparison of a text number
  with an integer that SQLite answered by type order is answered by value.

## Copying the record in: `ammit import-sqlite`

```
ammit import-sqlite -from /data/ammit.db [-batch 5000] [-recent 48h]
                    [-tables events,runs,...] [-skip-document-search] [-verify]
```

The same binary, the same `AMMIT_DSN` and Vault settings. It makes the schema
(the same `migrate` the service runs), a partition for every month the events
fall in, and copies:

- **append** tables - `events`, `search_text`, `calls`, `turns`, `suites`,
  `heal_laps`, `judgements`, `gates`, `limits`, `documents`, `deploys` - by
  key, above the highest key the target already has, one `COPY` per batch, each
  batch its own transaction;
- **tail** tables - `model_answers`, `model_idle`, whose rows learn their model
  after they are written - the same, after giving back and re-reading the last
  `-recent` of them;
- **mirror** tables - `runs`, `flows`, `queue`, `leases`, `watchdog_*`,
  `coverage`, `evidence`, `kb`, `kb_docs`, `kb_chunks`, `lift_marks`,
  `model_streams`, `model_of`, `phase_model_times`, `search_meta` - replaced
  whole in one transaction each run.

Then every id sequence is set above the highest id copied. `search_meta` comes
with the rest, so the Postgres ammit does not re-read every event for search
on its first start. `prices` is not copied: it is seeded from `prices.json` on
every start.

The source is opened read-only (`mode=ro`) and read one batch per statement, so
it never holds SQLite's WAL open for long and never writes to the file.
Values that do not fit their column are coerced and counted (a NUL in text, a
`\u0000` or lone surrogate in a payload, a non-number in a number column); a
source column with nowhere to go stops the copy rather than drop it.

It is safe to run as often as wanted. Each run copies what the target does not
have; `-verify` copies nothing and prints, per table, the row count and highest
key on each side.

Measured on a scratch copy: a SQLite file filled by the SQLite build and copied
by this tool answered 170 of 173 endpoint and panel questions identically to
the SQLite service over the same file, and the raw table dumps through `/query`
byte for byte. The three that differ are a deploy's age (time-dependent), one
float sum on a rounding boundary and the knowledge base's score scale.

## The cut-over

Nothing below has been run. It needs the three PRs and about ten minutes with
the watchdog stopped, at the end.

### Before (the old ammit keeps running)

1. **Merge the agentic-v-model clients PR** (`ammit-postgres-clients`). Its SQL
   reads the same on SQLite, so this changes nothing yet; it removes the
   lockstep.
2. **Put the password in Vault**, once, from the Vault container with the root
   token - never echoed, never in a file:

   ```
   docker exec -it vault sh -c 'VAULT_TOKEN=<root> vault kv put sut/ammit/postgres.env \
     content="POSTGRES_PASSWORD=$(head -c 32 /dev/urandom | od -An -tx1 | tr -d " \n")"'
   ```
3. **Merge the compose PR** (`ammit-postgres-compose`) and start only the
   database:

   ```
   cd ~/work/agentic-v-model/deploy
   docker compose -f ammit-compose.yml --profile postgres up -d ammit-postgres
   docker compose -f ammit-compose.yml --profile postgres ps ammit-postgres   # healthy
   ```
   The running ammit is not touched (no `--force-recreate`, no other service).
4. **Build the new image under its own tag**, from this PR's commit, so the
   running container's image is not replaced:

   ```
   docker build -t ammit:postgres <checkout of this PR>
   ```
5. **The bulk copy, while the old ammit works.** A one-off container on the
   stack network with the data volume (read-write mount; the tool opens the file
   read-only and SQLite needs to touch `-shm` to read a WAL database):

   ```
   docker run --rm --network agentic-v-model_default \
     -v agentic-v-model_ammit-data:/data \
     -e AMMIT_DSN='postgres://ammit@ammit-postgres:5432/ammit?sslmode=disable' \
     -e AMMIT_PG_VAULT=ammit/postgres.env -e VAULT_ADDR=http://vault:8200 \
     -e SUT_VAULT_TOKEN \
     ammit:postgres import-sqlite -from /data/ammit.db
   ```
   `SUT_VAULT_TOKEN` is the one in `deploy/.env`. Add `-skip-document-search`
   if #158 is in: those rows are deleted on the first start anyway, and they
   are 8 of the 14 GB. Run it again (it copies the delta) as often as you
   like; `-verify` shows how close the two are.

   While the old ammit runs, its daily `archive` can move a finished run out of
   SQLite after its events were copied: Postgres keeps those events without
   their `runs` row. Harmless, but `retention.days` raised through the limits
   API for the migration days avoids it.

### The window (watchdog stopped for minutes)

6. Pick a moment with nothing running: `GET /inflight` empty, nothing
   `running` in `GET /queue`.
7. `docker stop ammit`. The gateway buffers every record for it meanwhile
   (`RECORD_BUFFER_ITEMS`, `RECORD_BUFFER_MB`, `RECORD_MAX_AGE_S`).
8. The last delta and the check:

   ```
   docker run --rm ... ammit:postgres import-sqlite -from /data/ammit.db
   docker run --rm ... ammit:postgres import-sqlite -from /data/ammit.db -verify   # every table "same"
   ```
9. Merge this PR, put `~/work/ammit` on it, and bring ammit up on the new
   build: `python3 deploy/stack.py build`, then
   `docker compose -f deploy/ammit-compose.yml up -d ammit`.
10. Check: `GET /health` says `postgres://ammit-postgres:5432/ammit`; `/runs`,
    `/watchdog`, `/search?q=...` and the charts page answer; the gateway's
    buffer drains (its log).
11. Put the saved panels back in Postgres SQL:
    `curl -X POST localhost:8099/charts/local --data @docs/charts-local.postgres.json`
    (port by hand any panel saved after 2026-11-06 first).
12. Take the `profiles: ["postgres"]` line off `ammit-postgres` (a one-line
    compose PR), so `stack.py up` keeps the database up from now on.

The SQLite file stays where it is, untouched, for the rollback.

The monthly SQLite archives (`/data/archive/ammit-YYYY-MM.db`) are not copied:
they stay SQLite files, read with `sqlite3` as before. Loading them into the
`archive` schema is a later, separate step - their ids are below the live
ones, so `import-sqlite`'s append-by-key would skip them; it needs a
`-into archive` mode that does not exist yet.

## Rollback

- **Before step 7**: nothing has changed for anyone. Stop `ammit-postgres`;
  drop its volume if the copy is to be thrown away.
- **After the cut-over**: stop the new ammit, put `~/work/ammit` back on the
  last SQLite commit, `stack.py build`, `up -d ammit`. It opens
  `/data/ammit.db` exactly as it was at step 8. The clients need nothing: their
  SQL reads on both.
  What the SQLite file does not have is what arrived after the cut-over. If
  that matters, re-post it before restarting the old build's traffic - every
  event since the last id the import copied, with its `at`:

  ```
  # on the Postgres ammit, before stopping it: ids above the cut-over's
  curl -s --get localhost:8099/query --data-urlencode \
    "sql=SELECT at, payload FROM events WHERE id > <last copied id> ORDER BY id" > after.json
  # then, on the SQLite ammit:
  python3 -c 'import json,sys,urllib.request as u
  for at, p in json.load(open("after.json"))["rows"]:
      e = json.loads(p); e["at"] = at
      u.urlopen(u.Request("http://localhost:8099/events", json.dumps(e).encode(),
                          {"Content-Type": "application/json"}))'
  ```
  Re-posting re-derives the lifted tables (turns, calls, gates, answers) the
  way ingest always does. Rows written outside events - a queue row, a lease,
  a watchdog cycle, a coverage or knowledge-base write - are not in it; for a
  rollback within hours there are few, and they are in the Postgres database
  to read.
- **The database is the Postgres one from then on**: `pg_dump` of
  `ammit-pg-data` is the backup the SQLite file used to be by being a file.
